# Plan T-041 — Extracción por visión (`pnpm extract`)

Spec: `specs/SPEC-E-content-tools.md` §T-041 · Deps: T-002 (DONE), T-045 (REVIEW, código fusionado y verde) · Modelo: M

## Alcance
`pnpm extract <carpeta-de-fotos> [--out content/pokemon/_staging] [--dry-run]`: por cada foto
(jpg/jpeg/png/webp, orden alfabético) arma el prompt de CARD-INGESTION §3, lo envía a un
modelo con visión y escribe:
- `_staging/<foto>.json` `{ _comment, photo, cards }` con las cartas válidas.
- `_staging/_errors/<foto>.json` `{ _comment, photo, errors: [{ issues, card }] }` con las
  inválidas y el motivo (issues formateados con `formatIssues` de content/validate).

## Decisiones
- Patrón T-043/T-045: cliente inyectado `VisionClient(photo, prompt) → {ok,text} | {ok:false,error}`
  ⇒ núcleo testeable sin red. Default: API compatible con OpenAI (`fetch`), config por env:
  `VISION_API_KEY` (obligatoria), `VISION_API_URL` (default `api.openai.com/v1/chat/completions`),
  `VISION_MODEL` (default `gpt-4o-mini`). `.env` ya está gitignored ⇒ jamás commiteada.
- Prompt: reglas de CARD-INGESTION §3 **verbatim** (exportadas para testear la copia literal)
  + resumen del esquema **derivado del código** (Stage/CardGroup/options de `EffectSchema`,
  ELEMENTS, FX_ARCHETYPES, OfficialMoveStatus). Nada duplicado a mano.
- Normalización tolerante pre-Zod (`normalizeCard`, exportada): stage "Básico/Evolución" →
  basic/evolution (el prompt verbatim usa etiquetas en español), ints desde strings numéricas
  (dex/hp/chances/damage.base/ifRoll.damage/xp), `source.photo` = nombre real de la foto,
  `source.verified=false` si falta. El resto queda tal cual.
- Se escribe la carta normalizada **cruda** (no el dato parseado): `needsReview`/`position`
  sobreviven como claves extra (visibles en /admin/cards) y el archivo igual valida
  (`PokemonFileSchema` descarta desconocidos). Recuento de `custom` con `countCustomEffects`
  sobre las cartas parseadas; `needsReview` se cuenta del raw.
- Respuesta del modelo: `parseModelJson` tolerante (fences ```json, array/objeto embebido);
  acepta array o `{cards:[...]}`. Foto sin JSON ⇒ falla de foto (reporte), no `_errors`.
- `--dry-run` (AC-3): lee `<fotos>/_recordings/<base>.json` como respuesta grabada; no toca
  la red ni exige `VISION_API_KEY`; grabación faltante ⇒ foto fallada.
- Exit codes: 2 mal uso / falta `VISION_API_KEY` sin `--dry-run`; 1 fotos falladas o 0 fotos;
  0 resto (cartas inválidas en `_errors` son resultado esperado — OWNER-REVIEW mide la tasa).
- Informe (AC-4): `extract: N foto(s) · M carta(s) · R needsReview · C custom · I inválidas (_errors) · F falladas`.
- `_staging/_errors` es subdirectorio ⇒ el listado de /admin/cards lo salta (solo archivos).
